## Resume executif

Volt est un projet **fondamentalement sain et exceptionnellement durci** : le pipeline de scoring Rust est bien optimise (matcher zero-copie, top-K, transactions WAL), le sandbox d'extensions est de qualite professionnelle (SSRF multi-forme, re-validation par hop, eval/Function neutralises, fail-closed sur tampering), et l'edition Rust 2024 est en place. Les vraies faiblesses sont **structurelles et non fonctionnelles** : un re-envoi par IPC de tout le catalogue d'apps (icones base64 incluses) a chaque frappe (le goulot #1 mesure), une absence totale d'audit de vulnerabilites en CI alors que le projet embarque un runtime ONNX natif en release-candidate, et une dette de typage masquee par ~30 double-casts `as unknown as` plutot que des unions discriminees. S'y ajoutent des god-files (extensions.rs 3480L, worker-sandbox.ts 1500L, SettingsApp.tsx 2152L), 8-9 violations directes de la regle ESLint zero-tolerance de CLAUDE.md, et une derive documentaire majeure (notes/RAG/auth/sync invisibles dans la doc d'archi). React Compiler n'est pas active alors que la memoisation manuelle est cassee (218 hooks memo pour 1 seul `React.memo`). **Verdict : architecture de production solide a consolider, aucun finding critique en securite, mais plusieurs quick-wins a fort ROI (IPC, code-split, audit CI, deps mortes) qui ameliorent directement le temps frappe→resultat et la posture supply-chain.**

## Problemes par theme

### Modernisation React (Compiler + useEffect + listes)

- **[medium] React Compiler non active alors que la memoisation manuelle est cassee (218 hooks memo / 1 seul `React.memo`)** — `vite.config.ts:12` (react() nu), `eslint.config.js:142-144`, `ResultItem.tsx:136-137`, `NoteListItem.tsx:100`. Le seul composant memoise du repo est `NoteListItem`. Les ~218 `useCallback`/`useMemo` (55 fichiers) sont quasi tous inutiles car les enfants ne sont pas `React.memo`. `ResultItem` (hot-path, rendu N fois) souscrit a `useSearchStore((s) => s.searchQuery)` → re-render integral a chaque frappe ET chaque `selectedIndex`. **En 2026** React Compiler est stable et c'est le standard pour eliminer la memoisation manuelle ; la stack (`@vitejs/plugin-react@4.7`, `react@19.2`, `eslint-plugin-react-hooks@7.1`) est exactement la cible. **Refonte** : activation progressive (mode `annotation` → annoter `ResultItem`/`ResultsList`/`NoteListItem` → mode `infer` apres CI verte + smoke webview), puis suppression progressive des hooks morts. Prerequis : corriger les violations set-state-in-effect (ci-dessous).

- **[medium] Bus d'evenements DOM `volt:*` parallele a Zustand : ~18 useEffect dans App.tsx pour de la navigation** — `App.tsx` (volt:open-timer:208, volt:open-ai-chat:225, volt:open-quick-ai:243, volt:open-create-extension:369, volt:open-manage-extensions:374, volt:toast:305, volt:hud:319), `searchStore.ts:30-40`, `uiStore.ts`. Trois mecanismes de coordination coexistent (3 stores Zustand + bus DOM + events Tauri). Chaque event de navigation force un couple `useCallback`+`useEffect` pour faire seulement `setActiveView()`. **En 2026** sur Zustand le pattern idiomatique est une action de store typee (`uiStore.openTimerView()`), pas un `CustomEvent` re-ecoute — le bus DOM contourne le typage et masque les transitions au devtools. **Refonte** : remplacer les events intra-renderer de navigation par des actions typees sur `uiStore` ; reserver le bus DOM/Tauri aux vraies frontieres (worker sandbox, inter-fenetres). Supprime ~6 couples useCallback/useEffect.

- **[medium] Derived-state stockee en state + bug de shadowing `gridColumns` dans l'emoji picker** — `EmojiPickerView.tsx:57` (`displayedEmojis` en useState alors que derivable), synchro imperative `updateDisplayedEmojis()` 76-98 rappelee a la main (104, 111) + effet de mount (66-71). **Bug reel** : `gridColumns` est un state calcule depuis la largeur (`:63`, utilise pour le CSS `:310`) mais `handleKeyDown` redefinit `const gridColumns = 7` (`:133`) qui shadow le state → les fleches Haut/Bas sautent toujours de 7 meme si le grid affiche un autre nombre de colonnes → **navigation clavier desalignee du rendu**. **En 2026** tout ce qui se calcule de props/state se derive en render/`useMemo`, jamais via un state miroir. **Refonte** : `displayedEmojis` → `useMemo(allEmojis, selectedCategory, searchQuery)` (supprime l'effet + 2 appels imperatifs + l'eslint-disable) ; supprimer le `const gridColumns = 7` local et reutiliser le state pour le pas de navigation.

- **[medium] Listes longues non virtualisees : 1800+ emojis montes d'un coup** — `EmojiPickerView.tsx:312-331` (`.map` sans virtualisation, ~1800 boutons, handler inline par item), `ResultsList.tsx:169-176,205-212` (handlers inline recrees par item), `ResultItem.tsx`. Chaque fleche re-render les 1800 boutons. **En 2026** le standard pour des listes de centaines d'items est la virtualisation (`@tanstack/react-virtual`). **Refonte** : virtualiser le grid emoji (et clipboard/files), extraire un `EmojiCell` memoise avec handler par-id stable. Pour `ResultItem`, le compiler suffit (liste bornee a 8).

- **[medium] Vues lourdes en eager dans ViewRouter : pas de React.lazy/Suspense** — `ViewRouter.tsx:1-22` importe statiquement TOUTES les vues secondaires (AiChatView, GameView, EmojiPickerView +1800 emojis, ManageExtensionsView, ChangelogView...). Meme avec le chunk `plugins-builtin`, il est importe synchroniquement via ViewRouter. **En 2026** on ne charge pas un editeur riche / dashboard de metriques au boot d'un launcher. **Refonte** : `const X = lazy(() => import(...))` + `<Suspense>` autour du switch ; garder en statique seulement SearchBar/ResultsList/Suggestions. (Voir le finding perf jumeau bundle-coldstart-01 ci-dessous, mesure ~1 Mo → ~0.5 Mo.)

- **[low] `forwardRef` deprecie + setState-in-effect dans SlashCommandMenu** — `SlashCommandMenu.tsx:1,31` (`forwardRef`), reset de selection via `useEffect(() => setSelected(0), [items])` (`:44-46`) → TipTap recree le tableau a chaque frappe = render supplementaire systematique. **En 2026** en React 19 `ref` est une prop standard. **Refonte** : supprimer `forwardRef`, accepter `ref` en prop ; remplacer le reset par une derivation en render (comparer une ref a l'identite courante) ou un `key`.

### Violations CLAUDE.md : ESLint zero-tolerance contourne

- **[high] 8-9 directives `eslint-disable` / `@ts-expect-error` en code de production** — `ClipboardHistoryView.tsx:113`, `FileSearchView.tsx:172`, `EmojiPickerView.tsx:72,166`, `GameView.tsx:143`, `TimerView.tsx:235` (5x `react-hooks/exhaustive-deps`), `shell/index.ts:132`, `ansiParser.utils.ts:76` (2x `no-control-regex`), `registry.test.ts:267` (`@ts-expect-error`). - **[medium] Deux regles React Compiler desactivees dans la config masquent des setState-in-effect reels** — `eslint.config.js:146-147` (`react-hooks/set-state-in-effect: 'off'`, `react-hooks/immutability: 'off'`). Or `set-state-in-effect` detecterait precisement `SlashCommandMenu.tsx:44-46` et `EmojiPickerView.tsx:66-71`. **En 2026** ces regles (issues du compiler) rendent le codebase migrable ; les desactiver ferme les yeux sur les patterns qui cassent la memoisation auto. **Refonte** : re-activer (au minimum `'warn'`), traiter les violations au cas par cas. **Prerequis bloquant de l'activation du compiler.**

- **[high] I/O fichier synchrone (`std::fs`) dans des `#[tauri::command] async fn`** — `commands/extensions.rs:844,1084,1125,1414,1446,1478,1559,2130,2243,2261,2279,2286` (≈20 commandes async, un seul `spawn_blocking` dans 3480 L), `commands/notes.rs:80,739-819` (rusqlite synchrone derrière `std::sync::Mutex` dans 12 commandes async), `commands/ai_quick_actions.rs:49,110,113,126`, `commands/custom_emojis.rs:606,725,177` + `set_clipboard_image_with_retry` (`custom_emojis.rs:665-704`) qui appelle `std::thread::sleep` jusqu'à ~700 ms en plein `async fn custom_emojis_copy_image`. Ces opérations parquent un worker thread Tokio. **En 2026** : Tauri exécute les commandes async sur le runtime Tokio multi-thread partagé ; un `read_to_string`/`fs::write`/`thread::sleep` synchrone bloque un thread du pool, et sous charge (rescan extensions + sync + indexer) on peut affamer le runtime et figer toute l'IPC. `apps.rs` et `embeddings/mod.rs` montrent que l'équipe sait faire (`spawn_blocking` + timeout) — c'est juste inégalement appliqué. **Refonte** : pour le fichier, soit `tokio::fs` (déjà en dépendance, utilisé 1× seulement), soit déplacer la logique SQLite/fs synchrone derrière `tokio::task::spawn_blocking` (comme `files.rs`/`embeddings.rs`) ; remplacer le `std::thread::sleep` de `set_clipboard_image_with_retry` par un `spawn_blocking` autour de toute la boucle arboard, ou rendre la fonction non-async et l'appeler via `spawn_blocking`.

Le `Box<dyn Plugin>` stocké n'est utilisé que pour `id()/name()/is_enabled()` (sync). **En 2026** : un trait async object-safe via `#[async_trait]` qui boxe chaque future n'a de sens que si on dispatch effectivement de l'async sur le `dyn` — ici c'est du code mort qui paie le coût (allocation `Box<dyn Future>` à chaque appel + dépendance) pour rien, et masque le fait que le cycle de vie des plugins n'est pas réellement géré. **Refonte** : soit câbler réellement `initialize_all` (itérer et `plugin.initialize().await` sur les `Box<dyn Plugin>`), soit retirer `initialize/shutdown` du trait et les garder en méthodes inhérentes sur les types concrets (cf. point bilan).

Il n'y a donc **aucun besoin d'object-safety async** : le dispatch dynamique ne porte que des méthodes sync. Action : sortir `initialize`/`shutdown` du trait `Plugin` (les garder en méthodes inhérentes `async fn` sur `ClipboardManagerPlugin`/`SystemMonitorPlugin`, ce qui compile nativement depuis Rust 1.75 sans macro), puis supprimer `async-trait = "0.1"` du `Cargo.toml`. Si à l'inverse on veut *vraiment* un cycle de vie de plugins piloté par le registre sur `dyn Plugin`, alors `#[async_trait]` reste nécessaire (les RPITIT/`async fn in trait` natifs ne sont toujours pas object-safe en 2026 pour `Box<dyn Trait>`) — mais dans l'état actuel du code, la macro ne sert à rien et doit partir.

### Filet de tests — état des lieux & plan priorisé (deep-dive)

> _Cette section corrige l'axe « Tests » du premier passage (qui avait renvoyé 0 finding). Le filet est nettement plus solide qu'estimé — le verdict du tableau de bord est relevé de « Fragile » à « Correct, trous ciblés »._

**État des lieux.** Le constat « 26 fichiers TS / 0 test renvoyé » sous-estime largement la réalité côté back et surestime le vide côté front. Inventaire réel : **27 fichiers `*.test.ts(x)` dans `src/`** (~340 cas `it()`/`test()`), dont la majorité sont de vrais asserts et non des smoke (calculator/math 24 cas, timer 46, quicklinks 25, shell 21, websearch 17, registry 19, queryParser 14). Côté Rust : **271 `#[test]`/`#[tokio::test]` répartis sur 43 fichiers** — c'est le gros morceau ignoré par le premier passage. Les chemins sécurité critiques sont en fait **majoritairement couverts** : `launch_validation.rs` (8 tests : LOLBIN, trailing-space NTFS, ADS `:Zone.Identifier`, injection UWP `cmd.exe!x`), `extension_state_sig.rs` (5 tests : sig path, write atomique no-key, NoSignature/KeyUnavailable), `commands/shell.rs` (32 tests : blocklist, NFKC quote-strip, redacteurs GitHub/AWS/Stripe/Slack/JWT, working-dir UNC/NT), `commands/auth.rs` (7 tests : CSRF state TTL, kid manquant, non-JWT, PKCE). Le SSRF de `worker-sandbox.ts` **est testé en isolation** (`worker-sandbox.test.ts`, 11 cas : décimal/hex/octal IPv4, IPv4-mapped IPv6, link-local) — contrairement au constat initial. Le bench criterion **est branché** (`[[bench]]` + `harness = false` dans `Cargo.toml`, dev-dep `criterion 0.5`). Les **e2e Playwright sont réels** (5 specs, mock IPC complet `__TAURI_INTERNALS__`, parcours clavier/ARIA/calculator/debounce). Coverage Vitest configuré (provider v8) avec seuils **uniquement sur 2 cibles** (registry, calculator) — aucun seuil global. Les vrais trous sont ailleurs : formule de frecency, contrat Rust→TS, parité des blocklists dupliquées, `sanitizeFetchOptions`, et la branche alg-confusion réelle de l'auth.

- **[high] Branche alg-confusion + validation de claims JWT non testée** — `src-tauri/src/commands/auth.rs:744-766`. Les 7 tests existants s'arrêtent aux gardes pré-réseau (kid manquant, non-JWT) ; le rejet réel `header.alg != jwk_alg` (l.745), la vérif de signature contre la JWK, et les checks `iss`/`aud`/`exp` (l.760-766) ne sont jamais exercés faute de fixture JWKS. **En 2026** c'est la défense centrale contre le token-forgery (HS256 plaqué sur une clé ES256) ; une régression silencieuse ici = bypass d'authentification complet, et c'est exactement le type de bug qu'un refactor de `jsonwebtoken` v10 peut réintroduire. **Refonte** : créer `auth_jwt_validation.rs` (test integration) avec une paire EC P-256 générée en test, un mini-JWKS en mémoire, et asserter : (a) token ES256 valide → `Ok(claims)`, (b) même payload signé HS256 avec la clé publique comme secret → `Err` alg mismatch, (c) `exp` expiré → `Err`, (d) mauvais `aud`/`iss` → `Err`.

- **[high] Aucun test de parité des deux blocklists shell dupliquées** — `src/features/plugins/builtin/shell/index.ts:32` vs `src-tauri/src/commands/shell.rs` (BLOCKED_PATTERNS). Le commentaire (`index.ts:8-10`) reconnaît la duplication ; or les listes **ont déjà divergé** : le Rust bloque `Stop-Computer`/cmdlets PowerShell, `init 0`/`telinit`, `-EncodedCommand`, `reg.exe` ; le front ne bloque ni les cmdlets PowerShell ni les commandes encodées. Un seul test de parité (style `i18n-parity.test.ts`, qui existe déjà et marche) attraperait toute dérive future. **En 2026** une blocklist front/back désynchronisée donne un faux sentiment de sécurité UX et masque les régressions de durcissement. **Refonte** : `src/features/plugins/builtin/shell/blocklist-parity.test.ts` qui charge un corpus partagé de ~25 commandes dangereuses (rm -rf, fullwidth, Stop-Computer, init 0, encoded) et asserte que `isCommandBlocked` (front) renvoie `true` sur **exactement** le même ensemble que la liste Rust de référence (corpus en fixture JSON commune).

- **[high] Bypass Unicode/homoglyphe de la blocklist shell jamais exercé** — `src-tauri/src/commands/shell.rs:178-200` (`normalize_for_blocklist` via NFKC). Le code documente explicitement la défense fullwidth/compatibilité (l.170-172) mais **aucun test ne nourrit un caractère non-ASCII** : `test_block_quoted_*` ne couvrent que le strip de guillemets. La normalisation NFKC est la seule barrière contre `ｒｍ -rf /` (fullwidth) ou les formes de compatibilité. **En 2026** les bypass par normalisation Unicode sont un classique des audits ; sans test, un `nfkc()` accidentellement retiré passe inaperçu. **Refonte** : ajouter dans le module `tests` de `shell.rs` un `test_block_fullwidth_rm_rf` (`"\u{FF52}\u{FF4D} -rf /"`) et un cas de forme de compatibilité, asserter `is_command_blocked(...) == true`.

- **[med] Formule de frecency (décroissance temporelle) non testée** — `src-tauri/src/launcher/history.rs:522-548`. Les 4 tests couvrent `launch_count`, pin, tags — mais **pas** le `recency_weight = (-age_hours / 168.0).exp().max(0.2)` (half-life 1 semaine) ni `count_factor * recency_weight`. C'est le cœur du ranking : un lancement d'il y a 1h doit primer un lancement d'il y a 1 mois à count égal. **En 2026** un refactor du scoring (le git log montre `perf: top-K BinaryHeap`) peut inverser le tri sans qu'un test ne bronche — dégradation UX silencieuse. **Refonte** : `test_frecency_recency_decay` injectant deux records même `count` mais `last_launched` à 1h vs 240h, asserter que le score récent est strictement supérieur et que le plancher `0.2` tient au-delà de ~3 semaines.

- **[med] `sanitizeFetchOptions` (durcissement réseau extension) non testé** — `src/features/extensions/loader/worker-sandbox.ts`. Seul `isUrlSafe` est couvert (`worker-sandbox.test.ts`). Le stripping des en-têtes `Cookie`/`Authorization`, l'omission des credentials, le rejet du SSRF par redirection et le cap de 10 MB (tous listés dans CLAUDE.md « SSRF prevention ») n'ont **aucun assert** (grep `sanitizeFetchOptions|Cookie|redirect|credentials` → 0 hit dans le test). **En 2026** une extension malveillante exfiltre via en-têtes ou redirige vers une IP privée ; ces contre-mesures sont du code de confiance non régressé. **Refonte** : étendre `worker-sandbox.test.ts` avec un `describe('sanitizeFetchOptions')` asserant que `Cookie`/`Authorization` sont retirés, `credentials` forcé à `omit`, et qu'une option `redirect` non-`error`/`manual` est neutralisée.

- **[med] Évasions de sandbox du Worker bootstrap non couvertes** — `src/features/extensions/loader/worker-bootstrap.ts` (vs `index.test.ts`). CLAUDE.md affirme « eval/Function/WebSocket/XMLHttpRequest/importScripts disabled » ; or `index.test.ts` teste le *chargement* d'un module transpilé (`evalModule`) mais **n'asserte aucune neutralisation** de ces globals (grep `eval|Function|WebSocket|importScripts` → uniquement un commentaire l.103). **En 2026** la promesse de sandboxing d'extensions tierces est un argument de sécurité produit ; sans test, un bootstrap régressé réexpose `Function`/`WebSocket`. **Refonte** : `worker-bootstrap.test.ts` chargeant un faux module qui tente `new Function('return 1')`, `new WebSocket(...)`, `importScripts(...)`, asserter que chacun lève/est `undefined` dans le realm sandbox.

- **[low] Aucun test de contrat Rust→TS (sérialisation camelCase / shape IPC)** — transverse (`invoke_handler!` dans `lib.rs` ↔ `common.types.ts`). `common.types.test.ts` valide des shapes TS mais **rien ne vérifie l'alignement** des `#[serde(rename_all = "camelCase")]` Rust avec les interfaces TS consommatrices (grep `rename_all|serde|contract` dans les tests → 0 hit pertinent). Le projet n'utilise pas `tauri-specta`. **En 2026** un champ renommé côté Rust casse le front au runtime sans erreur de compilation TS (les deux côtés compilent isolément) — c'est précisément la classe de bug « 2 tests de régression IPC seulement ». **Refonte** : soit adopter `tauri-specta` pour générer les types et un test de drift, soit a minima un `ipc-contract.test.ts` qui charge des payloads JSON-fixtures (capturés depuis de vrais retours Rust) et les `satisfies` contre les interfaces TS, faisant échouer le build si un champ disparaît.

- **[low] Bugs de release déjà commis (cycle de chunks v0.1.8, fallback keyring v3 mock) sans test de garde** — `vite.config`/`Cargo.toml`. Confirmé : aucun test ne détecte un cycle de chunks Rollup (le seul filet est le script manuel « Étape 3A » de CLAUDE.md, hors CI) ni la retombée silencieuse de `keyring` v3 sur son mock-store (les features `apple-native`/`windows-native` ne sont garanties que par un commentaire dans `Cargo.toml:68-74`, pas par un test). **En 2026** ces deux bugs ont causé des releases mortes (splash infini) et une casse d'auth totale ; ils sont assez déterministes pour être testables. **Refonte** : (a) porter le cycle-scan en test Vitest sur `dist/assets` exécuté en CI post-build ; (b) test Rust `keyring_roundtrip` qui `store` puis `retrieve` une valeur et asserte l'égalité — sur le mock-store il retournerait `NoEntry`, donc le test échouerait si les features backend sautaient.
