Findings against `dev` HEAD aa2e600 on 2026-05-09. Scope: only changes since v0.1.7 (May 6).

## New finding

**HIGH** -- `commands/quicklinks.rs::open_quicklink` (line 250) accepts a `Quicklink` struct over IPC, validates only that the program is an absolute path to an existing file with no shell metacharacters (via `validate_command_target`), then spawns the program directly via `std::process::Command`. There is no `validate_launch_path()` call.

**Impact:** Any frontend code (compromised dependency, malicious extension running outside the Worker sandbox, dev-tools tampering) can invoke `open_quicklink` directly with `{ link_type: "command", target: "C:\\Windows\\System32\\cmd.exe ..." }`. The target does not need to exist in the saved quicklinks store -- IPC accepts an arbitrary struct.
- Bypasses the LOLBIN denylist (`utils/launch_validation.rs::BLOCKED_EXECUTABLES`: cmd.exe, powershell.exe, regsvr32.exe, mshta.exe, certutil.exe, ...) that `launch_application` enforces.
- Combined with the multi-window single-capability surface, this is a one-IPC-call code-execution primitive.

**Fix:** In the `"command"` arm, after `validate_command_target`, also call `crate::utils::launch_validation::validate_launch_path(program)` and propagate Err. Consider also requiring `link_type=="command"` quicklinks to be looked up by id in the saved store, since IPC consumers should not fabricate arbitrary command targets.
